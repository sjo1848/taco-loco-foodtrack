﻿BLG-001 — BACKLOG DE CONSTRUCCIÓN MVP
Taco Loco Foodtrack
CuyoConsulting and Development
Fecha: 08/08/2026
Estado: CERRADO — Fase 6 Backlog / Readiness


1. PROPÓSITO
Convertir el alcance, UX/UI, diseño técnico y criterios QA del MVP en una secuencia ejecutable de construcción. Los tickets son deliberadamente pequeños, verificables e integrables. El backlog no agrega funcionalidades nuevas.


Fuentes canónicas:
• ALC-001 — Alcance funcional MVP.
• MEN-001 — Catálogo/modelo funcional.
• UX-001 — Flujos críticos.
• UI-001 / UI-002 — Dirección visual y blueprint.
• TEC-001 — Diseño técnico cerrado.
• QA-001 — Criterios de aceptación y Definition of Done.


2. REGLAS DEL BACKLOG
Prioridad P0: imprescindible para liberar el MVP.
Prioridad P1: mejora permitida solo después de P0 y únicamente si no expande alcance.


Reglas de ejecución:
• no comenzar construcción hasta superar el gate;
• un ticket debe poder verificarse de forma independiente;
• ningún ticket puede redefinir alcance o UX por conveniencia técnica;
• cada ticket implementa tests relevantes según QA-001;
• todo cambio de decisión canónica debe actualizar Drive antes de mergear;
• evitar PRs gigantes: dividir por capacidad si el cambio deja de ser revisable;
• no anticipar pedidos, carrito, POS, KDS, stock, pagos, delivery, analytics o multi-tenant.


3. ORDEN DE CONSTRUCCIÓN
C1 — Fundación técnica.
C2 — Catálogo, autenticación y media.
C3 — Frontend público.
C4 — Administración.
C5 — QA integrado / hardening.
C6 — Release y operación.

10. P1 — SOLO SI NO RETRASA RELEASE
No se presupone ejecución. Son ajustes dentro del alcance, no nuevas funcionalidades:
• pulido de microinteracciones no esenciales;
• mejora estética adicional de imágenes/recortes;
• optimizaciones medidas que no cambien arquitectura;
• refinamiento de observabilidad liviana.
Cualquier pedido que introduzca capacidad funcional nueva vuelve a Product/alcance y no se incorpora como “P1” silencioso.


11. DEPENDENCIAS CRÍTICAS DEL CAMINO AL RELEASE
Camino principal aproximado:
Gate aprobado → C1 → C2 → C3/C4 → C5 → C6 → release.


Dependencias externas no estructurales:
• cierre visual Fase 4 antes de tickets UI finales;
• dominio final antes de TL-051/TL-058;
• WhatsApp/admin/assets finales antes de TL-056;
• proveedor VPS antes de despliegue.
Estas dependencias no justifican cambiar la arquitectura.


12. CRITERIO DE READY — TICKET
Un ticket está Ready cuando:
• objetivo y alcance son inequívocos;
• dependencias previas están satisfechas;
• criterios QA aplicables están identificados;
• no depende de una decisión de negocio/UX/técnica no cerrada;
• puede desarrollarse y probarse sin inventar requisitos.


13. CRITERIO DE CIERRE DE BLG-001
BLG-001 puede cerrarse cuando:
• todos los requisitos P0 tienen al menos un ticket;
• cada flujo crítico de QA-001 está cubierto;
• dependencias permiten un orden ejecutable;
• no existen tickets fuera de alcance;
• Definition of Done puede aplicarse a cada incremento;
• el backlog permite iniciar TL-001 al abrirse el gate sin nueva fase de planificación.
