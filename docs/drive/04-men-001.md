1. PROPÓSITO
Transformar las cartas actuales de Taco Loco en una estructura funcional coherente, suficientemente precisa para alimentar UX, UI, modelo de datos e implementación sin arrastrar ambigüedades innecesarias.


Este documento NO diseña todavía la base de datos física. Define el modelo funcional del catálogo y la fuente canónica de categorías, productos, opciones y datos pendientes de validar.


2. PRINCIPIOS DE MODELADO
• Category representa agrupaciones navegables de productos.
• Product representa un ítem visible del menú con nombre, descripción, precio y estado operativo.
• ModifierGroup representa un grupo de opciones asociado a uno o más productos.
• ModifierOption representa una alternativa dentro de un grupo, por ejemplo una salsa.
• Availability representa el estado operativo disponible/agotado y cambia durante la operación.
• Published/Active controla si un producto o categoría aparece en el menú público.
• Featured es una marca simple de presentación, no una promoción con reglas comerciales.
• Image es opcional.
• El orden de categorías y productos debe poder controlarse.

7. ESTADOS FUNCIONALES
7.1 Categoría
• Activa: aparece en navegación si tiene contenido publicable según reglas UX/técnicas.
• Inactiva: no aparece públicamente.


7.2 Producto
Se distinguen dos dimensiones:
• Publicación: activo/publicado vs inactivo/no publicado.
• Disponibilidad: disponible vs agotado.


Esto evita confundir “no lo vendemos temporalmente porque se agotó” con “este producto ya no debe aparecer en el menú”.


8. ORDEN Y DESTACADOS
• Cada categoría tendrá sortOrder.
• Cada producto tendrá sortOrder dentro de su categoría.
• Un producto puede marcarse como featured=true.
• Featured no altera precio ni reglas de negocio; solo habilita tratamiento visual prioritario.


9. IMÁGENES
• Imagen de producto opcional.
• No todos los productos requieren fotografía.
• UX/UI decidirá qué productos se benefician de imagen y qué relación de aspecto se usará. Como fuente inicial se reutilizarán, cuando sea viable, los recortes/fotografías visibles en los flyers aportados.
• El modelo debe permitir reemplazar la imagen desde administración.
• La ausencia de imagen no impide publicar el producto. Cuando una imagen sea necesaria y el flyer no aporte material suficiente, podrá generarse una imagen coherente con el producto y la dirección visual definida en UI.

Criterios adicionales adoptados para UX/UI:

• normalización ortográfica: Pepperoni Premium;
• marcas/sabores concretos de bebidas: no se requieren para el MVP;
• fotografías: reutilizar primero material visible en los flyers y generar imágenes cuando no exista material adecuado.


11. DECISIONES QUE NO CORRESPONDEN A MEN-001
Se difieren a Diseño Técnico:
• tablas/colecciones físicas;
• IDs definitivos de base de datos;
• soft delete;
• auditoría;
• almacenamiento concreto de imágenes;
• API;
• framework;
• validadores técnicos.


Se difieren a UX/UI:
• si el producto abre modal/página o se lee inline;
• posición visual de destacados;
• comportamiento visual exacto de agotados;
• forma de mostrar salsas disponibles;
• diseño de tarjetas;
• navegación sticky;
• jerarquía de precios y descripciones.


12. CRITERIO DE CIERRE DE FASE 2
MEN-001 podrá marcarse CERRADO cuando:
• categorías estén acordadas;
• todos los productos actuales estén representados;
• opciones/modificadores necesarios estén modelados;
• no existan ambigüedades que obliguen a cambiar la estructura funcional;
• los pocos datos dudosos hayan sido confirmados o explícitamente aceptados como configuración posterior.
