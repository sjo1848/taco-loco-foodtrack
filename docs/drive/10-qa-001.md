1. PROPÓSITO
Definir criterios verificables de calidad y aceptación para el MVP antes de iniciar construcción. Este documento convierte ALC-001, MEN-001, UX-001, UI-001/UI-002 y TEC-001 en condiciones comprobables de implementación y release.


QA comienza antes del código: los criterios de este documento deben alimentar los tickets de construcción y verificarse durante cada incremento, no únicamente al final.

2. ESTRATEGIA DE PRUEBAS
La estrategia es proporcional al riesgo del MVP.


2.1 Unitarias
Cubren reglas puras y validaciones que pueden fallar sin navegador ni infraestructura externa:
• visibilidad de categorías/productos;
• disponibilidad vs publicación;
• ordenamiento;
• validación de precios;
• construcción del enlace WhatsApp;
• validaciones de dominio relevantes.


2.2 Integración
Cubren aplicación + PostgreSQL/Prisma y servicios técnicos críticos:
• repositorios de categorías/productos;
• transacciones;
• persistencia de disponibilidad/precio/publicación;
• relaciones de modificadores;
• sesiones/autorización;
• media mediante adaptador controlado cuando corresponda.


2.3 E2E
Cubren flujos críticos desde navegador:
• consultar menú público;
• login admin;
• cambiar disponibilidad;
• editar precio;
• crear/editar producto;
• publicación/despublicación;
• comportamiento del CTA WhatsApp.


2.4 QA manual/visual
Reservado para aspectos donde la automatización no reemplaza una revisión real:
• fidelidad UI;
• responsive;
• contraste/foco;
• legibilidad;
• experiencia táctil;
• recorte y calidad de imágenes;
• verificación real del QR y WhatsApp en teléfono.


3. NIVELES DE SEVERIDAD
BLOCKER — impide usar el sistema, compromete seguridad/datos o impide release.
CRITICAL — rompe un flujo principal sin alternativa razonable.
MAJOR — funcionalidad relevante incorrecta, pero existe alternativa o impacto limitado.
MINOR — defecto visual/cosmético o de baja incidencia que no bloquea el objetivo del MVP.


Release rule: no se libera con BLOCKER o CRITICAL abiertos. Un MAJOR requiere decisión explícita de aceptación de riesgo. MINOR puede diferirse si está registrado y no afecta accesibilidad, seguridad o comprensión.


4. CRITERIOS DE ACEPTACIÓN — MENÚ PÚBLICO


QA-PUB-001 — Acceso público
Dado un usuario sin sesión, cuando abre /menu mediante URL o QR, entonces accede al menú sin login, registro ni instalación.


QA-PUB-002 — Contenido útil inmediato
El primer viewport debe mostrar marca/contexto y acceso real al catálogo sin splash, onboarding ni pantalla intermedia artificial.


QA-PUB-003 — Categorías públicas
Solo se muestran categorías activas y no archivadas que tengan al menos un producto publicable según las reglas del catálogo. No se renderizan secciones vacías.


QA-PUB-004 — Productos públicos
Solo se muestran productos publicados, no archivados y pertenecientes a una categoría visible.


QA-PUB-005 — Información del producto
Cada producto visible presenta, cuando corresponda: nombre, precio, descripción/ingredientes, disponibilidad, imagen opcional y metadata de opciones/modificadores informativos.


QA-PUB-006 — Precio
El precio visible coincide con priceAmount vigente en persistencia y se presenta en formato argentino, por ejemplo $ 10.000. No se utilizan floats para almacenar precios.


QA-PUB-007 — Agotado
Un producto available=false continúa visible en su posición normal, mantiene nombre/precio/descripción y comunica textualmente “Agotado”. No depende solo del color.


QA-PUB-008 — Despublicado
Un producto published=false no aparece en el menú público y no se confunde visualmente con un producto agotado.


QA-PUB-009 — Categoría inactiva
Al desactivar una categoría, la categoría y sus productos dejan de ser visibles públicamente aunque los productos estén publicados.


QA-PUB-010 — Imagen opcional
La ausencia de imagen no rompe alineación, jerarquía ni legibilidad. No se exige placeholder fotográfico.


QA-PUB-011 — Destacados
Si existe al menos un producto publicable con featured=true, aparece la sección de destacados. Si no existe ninguno, la sección desaparece por completo y no deja espacio vacío.


QA-PUB-012 — Duplicidad de destacado
Un producto destacado también continúa apareciendo en su categoría canónica.


QA-PUB-013 — Navegación por categorías
Seleccionar una categoría en la navegación rápida lleva a su sección correspondiente sin introducir una página nueva.


QA-PUB-014 — Sin búsqueda pública
No existe búsqueda pública en el MVP.


QA-PUB-015 — Salsas/modificadores
Los modificadores se muestran como información. No se crea selección persistente, cantidades, carrito ni total de pedido.


QA-PUB-016 — WhatsApp visible
El CTA global “Pedir por WhatsApp” permanece accesible durante el recorrido móvil y no oculta contenido esencial.


QA-PUB-017 — WhatsApp correcto
Al activar el CTA se abre el destino configurado con el mensaje base configurado. El mensaje no inventa productos, cantidades ni total.


QA-PUB-018 — Retorno desde WhatsApp
Volver/cancelar desde WhatsApp permite continuar navegando el menú sin pérdida de un estado relevante del MVP.


QA-PUB-019 — Error de carga
Ante un error recuperable de carga, el usuario recibe un mensaje comprensible y una acción para reintentar cuando aplique. No se muestran trazas internas.


QA-PUB-020 — Datos sensibles
La respuesta/página pública no expone passwordHash, sesiones, secretos, credenciales de storage ni campos administrativos innecesarios.


5. CRITERIOS DE ACEPTACIÓN — AUTENTICACIÓN ADMIN


QA-AUTH-001 — Acceso protegido
/admin y toda mutación administrativa requieren sesión autenticada.


QA-AUTH-002 — Login válido
Credenciales válidas crean una sesión server-side y llevan directamente a Productos, sin dashboard introductorio.


QA-AUTH-003 — Login inválido
Credenciales inválidas mantienen al usuario en login, muestran un error claro y no revelan innecesariamente si el email existe.


QA-AUTH-004 — Preservación de identificador
Un login inválido no borra innecesariamente el email/usuario ingresado.


QA-AUTH-005 — Cookie
La sesión utiliza cookie HttpOnly; en producción también Secure. No se persisten JWT/tokens de autenticación en localStorage.


QA-AUTH-006 — Logout
Cerrar sesión invalida la sesión server-side y el acceso posterior a /admin requiere nuevo login.


QA-AUTH-007 — Sesión vencida
Una sesión vencida redirige a login con mensaje comprensible y no permite continuar mutaciones.


QA-AUTH-008 — Rate limiting
Intentos repetidos de login quedan sujetos a la protección/rate limiting definido por TEC-001 sin bloquear el flujo normal.


6. CRITERIOS — LISTADO ADMIN DE PRODUCTOS


QA-ADM-PROD-001 — Listado
El administrador puede listar productos mostrando al menos nombre, categoría, precio, estado de disponibilidad y acción Editar.


QA-ADM-PROD-002 — Búsqueda
La búsqueda simple localiza productos por texto de forma útil para operación. No forma parte del menú público.


QA-ADM-PROD-003 — Filtro
El filtro por categoría limita el listado sin alterar datos persistidos.


QA-ADM-PROD-004 — Estado publicado vs agotado
El listado distingue claramente “agotado” de “no publicado”.


QA-ADM-PROD-005 — Toggle rápido
Disponible ↔ Agotado puede cambiarse directamente desde el listado sin abrir el formulario completo.


QA-ADM-PROD-006 — Persistencia de toggle
Un cambio exitoso persiste en PostgreSQL y el menú público refleja el nuevo estado.


QA-ADM-PROD-007 — Error de toggle
Si la actualización falla, la UI informa el error y no deja al operador creyendo que el estado cambió cuando la persistencia conserva el valor anterior.


QA-ADM-PROD-008 — Pending
Mientras un toggle está guardando, se evita doble envío o estados simultáneos contradictorios.


7. CRITERIOS — CREAR / EDITAR PRODUCTO


QA-EDIT-001 — Campos
El formulario permite gestionar nombre, descripción, precio, categoría, imagen, disponibilidad, publicación, destacado, orden y modificadores permitidos por el modelo.


QA-EDIT-002 — Nombre
Nombre requerido, normalizado según validaciones técnicas y con error asociado al campo cuando no es válido.


QA-EDIT-003 — Precio
Precio requerido, entero positivo o cero únicamente si una regla futura lo admite explícitamente. Para el catálogo actual los valores deben ser positivos. Entradas inválidas no llegan a persistencia.


QA-EDIT-004 — Categoría
Todo producto publicable debe pertenecer a una categoría válida.


QA-EDIT-005 — Guardado
Guardar datos válidos persiste cambios y muestra feedback de éxito manteniendo contexto.


QA-EDIT-006 — Doble envío
Durante guardado se deshabilita/restringe un segundo envío equivalente.


QA-EDIT-007 — Validación
Errores de validación aparecen próximos a sus campos y preservan los valores corregibles ingresados.


QA-EDIT-008 — Error servidor/red
Un error no destruye innecesariamente datos locales del formulario; se comunica claramente qué ocurrió.


QA-EDIT-009 — Publicación
Cambiar published a false retira el producto del público sin borrar sus datos administrativos.


QA-EDIT-010 — Destacado
Cambiar featured afecta únicamente prioridad/presentación pública; no altera precio ni reglas comerciales.


QA-EDIT-011 — Orden
Cambiar sortOrder se refleja en el orden público correspondiente.


QA-EDIT-012 — Retiro lógico
No existe borrado irreversible como acción primaria. Cuando se utilice archivar, archivedAt retira el registro de vistas públicas sin pérdida accidental de información.


8. CRITERIOS — CATEGORÍAS


QA-CAT-001 — CRUD mínimo
Administrador puede listar, crear y editar categorías.


QA-CAT-002 — Activación
Puede activar/desactivar una categoría y el menú público refleja el cambio.


QA-CAT-003 — Orden
Puede controlar sortOrder y el orden público refleja el valor persistido.


QA-CAT-004 — Archivo
Archivar una categoría no equivale a agotarla y no debe producir exposición pública inconsistente.


QA-CAT-005 — Integridad
No se permite una operación administrativa que deje el catálogo público en un estado contradictorio sin una regla explícita de aplicación.


9. CRITERIOS — MODIFICADORES


QA-MOD-001 — Modelo canónico
Se pueden representar los grupos Salsa a elección, Carne a elección y Sabor de daikiri según MEN-001.


QA-MOD-002 — Reutilización
Un ModifierGroup puede asociarse a varios productos mediante ProductModifierGroup.


QA-MOD-003 — Cardinalidad por asociación
required/minSelections/maxSelections pertenecen a la asociación producto-grupo y no fuerzan una regla global idéntica para todos los productos.


QA-MOD-004 — Sin motor de pedido
El MVP no persiste selección de opciones del cliente, no calcula adicionales y no incluye priceDelta en el esquema inicial.


QA-MOD-005 — Carne genérica
“Carne a elección” se conserva como indicación genérica; no se inventan opciones concretas.


10. CRITERIOS — CONFIGURACIÓN / WHATSAPP


QA-SET-001 — Configuración
Administrador puede leer y modificar número/destino de WhatsApp y mensaje base.


QA-SET-002 — Validación
Destino/mensaje se validan server-side antes de persistir.


QA-SET-003 — Reflejo público
Cambios válidos se reflejan en el CTA público sin requerir cambio de código.


QA-SET-004 — Currency
La configuración usa ARS para este MVP.


11. CRITERIOS — IMÁGENES


QA-IMG-001 — Opcional
Un producto puede existir/publicarse sin imagen.


QA-IMG-002 — Autorización
Solo una sesión admin válida puede cargar/reemplazar imágenes.


QA-IMG-003 — Tipos
Se aceptan únicamente tipos configurados y validados realmente por contenido/MIME, con baseline JPEG, PNG y WebP.


QA-IMG-004 — Tamaño
Se rechazan archivos por encima del límite configurado; baseline inicial 5 MB antes de procesamiento.


QA-IMG-005 — Procesamiento
La imagen se procesa/optimiza server-side antes de publicarse y se limitan dimensiones excesivas.


QA-IMG-006 — Nombre seguro
La object key es generada por el sistema y no confía en el filename original del usuario.


QA-IMG-007 — Persistencia
Product almacena imageKey, no binarios ni una URL rígida dependiente del proveedor.


QA-IMG-008 — Reemplazo/cache
Reemplazar imagen genera una nueva key/version de modo que cache público no mantenga indefinidamente la imagen anterior.


QA-IMG-009 — Fallo
Si falla upload/procesamiento/storage, no se deja Product apuntando a un objeto inexistente como si la operación hubiera sido exitosa.


12. CRITERIOS — RESPONSIVE Y DISPOSITIVOS


Prioridad de validación:
1. teléfono;
2. tablet;
3. escritorio.


QA-RWD-001 — Mobile 360–390 px
El menú y admin son utilizables sin scroll horizontal involuntario, zoom obligatorio ni controles inaccesibles.


QA-RWD-002 — Tablet
La adaptación aprovecha el ancho sin cambiar arquitectura de información ni flujo funcional.


QA-RWD-003 — Desktop
Puede usar más columnas/ancho cuando corresponda, conservando el mismo contenido y reglas.


QA-RWD-004 — Navegación de categorías
En móvil la fila horizontal permanece utilizable por toque y scroll horizontal cuando sea necesario.


QA-RWD-005 — CTA inferior
El CTA móvil respeta safe-area y no tapa precio, navegación ni contenido final.


Baseline de navegadores para release:
• Chrome Android estable actual;
• Safari iOS estable actual;
• Chrome/Edge desktop estable actual;
• smoke test en Firefox desktop.
No se promete soporte a navegadores obsoletos no definidos por QA.


13. ACCESIBILIDAD
Objetivo: accesibilidad básica consistente con buenas prácticas WCAG AA aplicables al MVP; no se declara certificación formal.


QA-A11Y-001 — Contraste
Texto y controles mantienen contraste suficiente en estados normales, disabled y focus.


QA-A11Y-002 — Foco
Controles de teclado en admin/escritorio muestran foco visible.


QA-A11Y-003 — Táctil
Objetivos táctiles importantes apuntan a mínimo aproximado 44×44 CSS px.


QA-A11Y-004 — Estado no solo color
Agotado, error, éxito y disponibilidad nunca dependen únicamente de rojo/verde/color.


QA-A11Y-005 — Labels
Inputs tienen etiquetas/nombres accesibles y errores asociados comprensiblemente.


QA-A11Y-006 — Semántica
Encabezados, navegación y controles usan semántica apropiada; acciones interactivas no se implementan como elementos sin rol/teclado.


QA-A11Y-007 — Imágenes
Imágenes informativas tienen texto alternativo útil; decorativas pueden omitirse de tecnologías asistivas.


QA-A11Y-008 — Hover
Ninguna función crítica depende únicamente de hover.


14. PERFORMANCE Y EXPERIENCIA PERCIBIDA
No se introduce una métrica artificial que fuerce sobreoptimización antes de medir. Los siguientes criterios son de release:


QA-PERF-001 — Texto independiente de imagen
Nombre/precio/descripción pueden renderizarse aunque las imágenes aún estén cargando.


QA-PERF-002 — Imágenes
Las imágenes de catálogo se sirven optimizadas y con carga diferida cuando corresponda.


QA-PERF-003 — JS/UI
No se incorporan animaciones o librerías pesadas sin necesidad funcional.


QA-PERF-004 — Consulta
El menú no produce un patrón N+1 evidente ni un número de consultas proporcional innecesariamente a cada tarjeta.


QA-PERF-005 — Red móvil
En una prueba representativa con datos reales y throttling móvil, el menú debe ser navegable y mostrar información textual útil antes de completar cargas no críticas.


QA-PERF-006 — Regresión
Si Lighthouse/Web Vitals u otra medición evidencia una regresión severa, el release se bloquea hasta identificar la causa; los números exactos se registran durante implementación y no se inventan en pre-construcción.


15. SEGURIDAD


QA-SEC-001 — Autorización
Toda mutación /admin o equivalente responde como no autorizada sin sesión válida.


QA-SEC-002 — Secrets
Ningún secreto se versiona en Git ni se envía al navegador.


QA-SEC-003 — Password
Contraseñas se almacenan únicamente mediante hash fuerte configurado según TEC-001; nunca texto plano o reversible.


QA-SEC-004 — Cookies
Cookies de sesión aplican HttpOnly y configuración segura de producción.


QA-SEC-005 — CSRF
Las mutaciones protegidas cuentan con mitigación adecuada al mecanismo de sesión/framework elegido.


QA-SEC-006 — Validación
Datos enviados por admin se validan en servidor incluso si también existe validación cliente.


QA-SEC-007 — Errores
No se muestran stack traces, SQL, secretos o detalles internos al usuario final.


QA-SEC-008 — PostgreSQL
La base de datos de producción no está publicada directamente a Internet.


QA-SEC-009 — R2
Credenciales de storage tienen privilegios mínimos necesarios.


QA-SEC-010 — Dependencias
CI ejecuta comprobaciones/auditoría de dependencias definida para el proyecto y no ignora vulnerabilidades críticas conocidas sin decisión explícita.


16. RECUPERACIÓN, BACKUP Y RELEASE


QA-OPS-001 — Volumen
PostgreSQL usa almacenamiento persistente; reiniciar/recrear app no borra datos.


QA-OPS-002 — Backup
Existe pg_dump automático diario hacia storage offsite.


QA-OPS-003 — Retención
La política inicial de retención implementa o mejora 7 diarios + 4 semanales.


QA-OPS-004 — Restore
Antes del primer release productivo se ejecuta al menos una restauración real de prueba y se documenta el procedimiento.


QA-OPS-005 — Migraciones
Una migración Prisma fallida detiene el despliegue; no se continúa como release exitoso.


QA-OPS-006 — Health
Existe healthcheck de aplicación/contenedor verificable tras deploy.


QA-OPS-007 — HTTPS
Producción sirve exclusivamente mediante HTTPS para navegación normal.


QA-OPS-008 — Logs
Errores de servidor/autenticación/uploads quedan registrados sin incluir contraseñas, tokens o secretos.


17. SMOKE TEST DE RELEASE
Ejecutar en producción o entorno de release controlado:
1. abrir URL pública desde celular;
2. recorrer categorías;
3. verificar producto con y sin imagen;
4. verificar producto agotado;
5. abrir CTA WhatsApp;
6. iniciar sesión admin;
7. cambiar disponibilidad y confirmar reflejo público;
8. cambiar un precio y confirmar reflejo público;
9. cargar/reemplazar una imagen de prueba si corresponde;
10. cerrar sesión y verificar protección;
11. comprobar HTTPS/healthcheck;
12. comprobar que backup programado está operativo;
13. verificar QR físico o arte final contra URL estable.


18. MATRIZ DE AUTOMATIZACIÓN
Automatizar obligatoriamente cuando sea estable y costo-efectivo:
• reglas de visibilidad/orden/precios;
• repositorios y transacciones críticas;
• auth/autorización;
• endpoints/acciones administrativas críticas;
• E2E de menú, login, disponibilidad y precio;
• build/typecheck/lint.


Mantener revisión manual para:
• calidad visual contra Penpot;
• food photography/recortes;
• experiencia real de touch/safe-area;
• CTA WhatsApp real en dispositivo;
• QR físico;
• restore de backup antes de release.


19. DEFINITION OF DONE — TICKET
Un ticket se considera Done únicamente si:
• cumple sus criterios de aceptación vinculados;
• no introduce funcionalidad fuera de alcance;
• código tipado/lint/build sin errores;
• tests automáticos relevantes pasan;
• agrega/actualiza tests cuando cambia una regla;
• manejo de loading/error/empty está cubierto cuando aplica;
• responsive y accesibilidad se revisaron cuando toca UI;
• seguridad se revisó para auth/input/upload/secrets cuando aplica;
• migraciones son revisables y reversibles/recuperables mediante estrategia adecuada;
• documentación canónica se actualiza si la decisión cambió;
• PR revisada/mergeada según flujo Git definido;
• no quedan TODO críticos ocultos.


20. DEFINITION OF DONE — MVP / RELEASE
El MVP está listo para release cuando:
• todos los tickets P0 están Done;
• no hay BLOCKER/CRITICAL abiertos;
• MAJOR abiertos tienen decisión explícita de riesgo o están resueltos;
• suite automática verde;
• build productivo correcto;
• smoke test completo aprobado;
• UI principal revisada contra Fase 4;
• responsive/accessibility pass realizado;
• seguridad mínima revisada;
• backup + restore probado;
• dominio/URL, WhatsApp y admin final configurados;
• QR apunta a URL estable;
• despliegue HTTPS y healthcheck operativos.


21. CRITERIO DE CIERRE DE QA-001
QA-001 puede cerrarse cuando:
• todos los flujos del MVP tienen criterios verificables;
• se definió qué automatizar y qué revisar manualmente;
• existe Definition of Done;
• seguridad, responsive, accesibilidad, errores, performance y recuperación están cubiertos;
• los criterios pueden mapearse a tickets de BLG-001 sin ambigüedad material.
