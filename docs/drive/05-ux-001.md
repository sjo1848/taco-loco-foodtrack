﻿UX-001 — FLUJOS CRÍTICOS Y ARQUITECTURA DE EXPERIENCIA
Taco Loco Foodtrack
CuyoConsulting and Development
Fecha: 07/08/2026
Estado: CERRADO — Fase 3 UX


1. PROPÓSITO
Definir cómo se usa el MVP antes de diseñar su apariencia visual. Este documento trabaja navegación, jerarquía, flujos, acciones, estados y comportamiento responsive. La identidad visual, paleta, componentes visuales y mockups high-fidelity corresponden a UI/Figma en la Fase 4.


Fuentes canónicas:
• ALC-001 — Alcance funcional MVP.
• MEN-001 — Catálogo y modelo funcional del menú, CERRADO.
• PRE-DEV-002 — Proceso profesional y gate de construcción.


2. ACTORES Y OBJETIVOS


2.1 Cliente
Contexto principal: persona frente al foodtruck o que recibió el QR/enlace y consulta desde un teléfono.
Objetivos:
• abrir el menú inmediatamente;
• encontrar una categoría o producto rápido;
• entender qué incluye y cuánto cuesta;
• saber si está disponible;
• identificar opciones relevantes;
• pasar a WhatsApp cuando quiera realizar el pedido o consultar.


2.2 Administrador / encargado
Contexto principal: uso operativo desde teléfono, ocasionalmente desde computadora.
Objetivos:
• entrar de forma segura;
• encontrar un producto rápido;
• marcar disponible/agotado con mínima fricción;
• cambiar precio, texto, imagen, categoría, orden y destacado;
• publicar/despublicar sin borrar información;
• recibir confirmación clara de cada cambio.


3. PRINCIPIOS UX DEL MVP
• Mobile-first real: el diseño parte de una pantalla de teléfono.
• Scan-to-content: el QR debe llevar directo al menú, sin splash, onboarding ni login.
• Menor cantidad de pasos posible.
• Precio, nombre y disponibilidad deben entenderse sin abrir otra pantalla.
• No ocultar información esencial detrás de interacciones innecesarias.
• No usar búsqueda, filtros complejos ni navegación multinivel si el tamaño actual del catálogo no lo justifica.
• Producto agotado permanece visible para evitar confundir ausencia con error del menú.
• Administración optimizada para tareas frecuentes: disponibilidad primero; edición completa después.
• Feedback inmediato ante acciones administrativas.
• Accesibilidad, legibilidad y performance forman parte de UX, no de una revisión tardía.


4. ARQUITECTURA DE INFORMACIÓN PÚBLICA


Entrada única principal: /menu


Estructura lógica:
Menú
├── Encabezado de marca / contexto mínimo
├── Destacados, si existen
├── Navegación rápida por categorías
├── Tacos
├── Nachos
├── Quesadillas
├── Pizzas
├── Más delicias
├── Bebidas
├── Tragos
├── Información de salsas disponibles cuando corresponda
└── Acción de pedido/contacto por WhatsApp


Decisión UX inicial: el catálogo se presenta como una página continua por secciones. No se crea una página separada por categoría para el MVP.


La navegación de categorías funciona como acceso rápido a la sección correspondiente y se mantiene accesible durante el recorrido. Su tratamiento visual exacto corresponde a UI.


5. FLUJO PÚBLICO PRINCIPAL — QR → MENÚ → WHATSAPP


Happy path:
1. Cliente escanea QR.
2. Navegador abre /menu.
3. Se muestra contenido útil inmediatamente.
4. Cliente identifica categorías.
5. Selecciona una categoría o hace scroll.
6. Lee productos, precios y disponibilidad.
7. Si necesita opciones, las comprende dentro del contexto del producto o mediante información complementaria de la sección.
8. Cuando decide pedir, activa “Pedir por WhatsApp”.
9. Se abre WhatsApp con el contacto y mensaje base configurados.
10. El pedido continúa por el canal tradicional de Taco Loco.


No existe en MVP:
• carrito;
• cantidades;
• selección de modificadores para armar pedido;
• checkout;
• confirmación de pedido dentro del sistema.


6. NAVEGACIÓN POR CATEGORÍAS


Decisión UX:
• navegación de una sola profundidad;
• categorías visibles en acceso rápido;
• al seleccionar una categoría, desplazamiento a su sección;
• la categoría activa puede reflejarse mientras se hace scroll si la implementación sigue siendo simple y estable;
• no hay subcategorías en el MVP.


No se incorpora búsqueda en Fase 1 del producto: el catálogo actual es lo suficientemente acotado para navegación por categorías.


7. PRESENTACIÓN FUNCIONAL DEL PRODUCTO


Cada producto debe permitir comprender sin navegación adicional:
• nombre;
• precio;
• descripción/ingredientes relevante;
• disponibilidad;
• imagen cuando exista y aporte valor;
• indicación de opciones, por ejemplo “carne a elección” o “1 salsa a elección”.


Decisión UX inicial: no se requiere una página de detalle para cada producto. El contenido esencial se muestra en el listado. Si UI necesita controlar densidad visual, podrá utilizar expansión/detalle ligero sin cambiar el flujo funcional ni introducir una nueva página obligatoria.


Para “carne a elección” se muestra esa indicación tal cual; el MVP no enumera carnes porque no existe selección de pedido dentro del sistema.


Para productos con salsa a elección, el producto indica “1 salsa a elección”. Las salsas disponibles pueden presentarse una sola vez como información complementaria para evitar repetir cinco opciones en cada producto.


8. PRODUCTO AGOTADO


Comportamiento:
• continúa visible en su posición normal;
• muestra estado “Agotado” de forma inequívoca;
• conserva nombre, descripción y precio;
• no se confunde con producto despublicado;
• no impide navegar ni usar WhatsApp para otros productos.


Un producto despublicado/inactivo, en cambio, no aparece en el menú público.


9. DESTACADOS


Featured es una prioridad de presentación, no una promoción comercial.


UX:
• si hay productos destacados, se muestran antes del catálogo general o en una zona de alta visibilidad;
• un producto destacado sigue apareciendo también en su categoría canónica;
• si no hay destacados, la zona no ocupa espacio vacío;
• no se implementan carruseles obligatorios ni mecánicas promocionales complejas.


10. WHATSAPP


El CTA global “Pedir por WhatsApp” forma parte del MVP.


Comportamiento:
• disponible desde el menú con acceso fácil en móvil;
• abre el número configurado del negocio;
• utiliza mensaje base configurable, por ejemplo “Hola, quiero hacer un pedido en Taco Loco.”;
• no presupone que el sistema conoce productos, cantidades ni total del pedido;
• cancelar o volver desde WhatsApp devuelve al usuario al navegador sin pérdida de estado relevante.


UI decidirá si el CTA es sticky, flotante o se integra en una barra inferior, siempre evitando tapar contenido.


11. ARQUITECTURA DE INFORMACIÓN ADMIN


Entrada: /admin


Estructura mínima:
Admin
├── Login
├── Productos
│   ├── listado
│   ├── filtro por categoría
│   ├── búsqueda simple si aporta velocidad operativa
│   ├── toggle disponible/agotado
│   └── editar producto
├── Categorías
└── Configuración mínima del menú/WhatsApp


No se requiere dashboard de métricas para el MVP. Tras login, el usuario entra directamente al área operativa de productos.


12. FLUJO ADMIN — DISPONIBILIDAD RÁPIDA


1. Administrador inicia sesión.
2. Entra al listado de productos.
3. Localiza el producto por categoría, scroll o búsqueda si está disponible.
4. Cambia Disponible ↔ Agotado directamente desde el listado.
5. El sistema persiste el cambio.
6. Se muestra feedback de éxito o error.
7. El menú público refleja el nuevo estado.


Esta es la acción operativa de mayor frecuencia y no debe requerir abrir el formulario completo de edición.


13. FLUJO ADMIN — EDITAR PRODUCTO


1. Administrador abre el producto.
2. Ve formulario con datos editables del alcance.
3. Modifica uno o varios campos.
4. Guarda.
5. El sistema valida.
6. Si es correcto, confirma éxito y mantiene contexto.
7. Si hay error, conserva los cambios locales cuando sea razonable y señala exactamente qué debe corregirse.


Campos funcionales:
• nombre;
• descripción;
• precio;
• categoría;
• imagen;
• disponibilidad;
• publicado/activo;
• destacado;
• orden;
• opciones/modificadores permitidos por el modelo.


No se ofrece borrado irreversible como operación principal; despublicar cubre el caso normal con menor riesgo.


14. FLUJO ADMIN — CATEGORÍAS


Funciones mínimas:
• listar;
• crear;
• editar nombre;
• activar/desactivar;
• ordenar.


Una categoría inactiva no aparece públicamente. UX técnica posterior definirá qué sucede con productos activos contenidos en una categoría desactivada; la recomendación funcional es que no sean visibles mientras la categoría esté inactiva.


15. ESTADOS TRANSVERSALES


Público:
• loading inicial breve;
• contenido normal;
• producto agotado;
• categoría sin productos publicables: no mostrar sección vacía;
• error de carga: mensaje claro y opción reintentar;
• imagen ausente: layout sigue funcionando sin placeholder obligatorio.


Admin:
• loading;
• guardando;
• guardado exitoso;
• error de validación;
• error de red/servidor;
• sesión vencida;
• listado vacío;
• imagen subiendo / error de imagen.


16. RESPONSIVE


Prioridad 1: teléfono.
Prioridad 2: tablet.
Prioridad 3: escritorio.


El mismo contenido y funciones deben seguir siendo comprensibles en todas las resoluciones. Desktop puede aprovechar más ancho, pero no introduce flujos diferentes.


17. ACCESIBILIDAD Y USABILIDAD MÍNIMA


• objetivos táctiles suficientemente grandes;
• contraste adecuado;
• texto legible sin zoom;
• jerarquía semántica de encabezados;
• precio expresado como texto, no solo gráficamente;
• estado agotado comunicado por texto y no únicamente color;
• foco visible para navegación con teclado en admin y escritorio;
• imágenes decorativas/informativas con tratamiento alternativo adecuado;
• feedback de error próximo al campo o acción que lo produjo.


18. PERFORMANCE PERCIBIDA


• sin pantalla de bienvenida artificial;
• contenido textual y precios no deben depender de que terminen de cargar todas las imágenes;
• imágenes optimizadas y carga diferida cuando corresponda;
• evitar animaciones pesadas;
• navegación de categoría debe sentirse inmediata.


19. IMÁGENES COMO ENTRADA A UI


Para Fase 4:
• se priorizará material visual de los flyers ya aportados cuando su calidad y encuadre sean aprovechables;
• no es requisito que todos los productos tengan foto;
• si falta una imagen necesaria para una composición aprobada, se podrá generar una alternativa coherente con el producto y la identidad Taco Loco;
• UI establecerá relación de aspecto, recorte, consistencia y tratamiento visual.


20. DECISIONES UX CERRADAS EN ESTA ITERACIÓN


• una sola página pública continua;
• navegación rápida por categorías;
• sin búsqueda pública para el MVP;
• producto entendible desde el listado;
• sin página de detalle obligatoria;
• agotado permanece visible;
• despublicado desaparece;
• destacados opcionales sin lógica promocional compleja;
• WhatsApp es salida global hacia el canal tradicional;
• admin entra directamente a productos;
• disponibilidad se cambia rápidamente desde listado;
• edición completa se realiza en formulario separado;
• no hay borrado irreversible como flujo principal;
• responsive y accesibilidad se consideran desde esta fase.


21. PUNTOS A CERRAR ANTES DEL ACTA UX


Quedan deliberadamente pocos:
• CTA de WhatsApp: CERRADO. Será un acceso persistente en móvil; UI definirá si se materializa como botón flotante, sticky o barra inferior sin tapar contenido.
• Destacados: CERRADO. Se conserva una sección superior condicional: aparece solo cuando exista al menos un producto featured; si no hay destacados, no ocupa espacio.
• Wireframes mínimos: CERRADO mediante especificación estructural en este documento; se trasladarán a alta fidelidad durante UI/Figma.
• Revisión QA UX: CERRADA. Los wireframes cubren happy path, agotados, errores, validación, responsive, accesibilidad mínima y feedback operativo.


Criterio de cierre de UX-001: flujos, jerarquía, estados y wireframes suficientes para que UI pueda diseñar sin redefinir comportamiento.


22. WIREFRAMES FUNCIONALES CERRADOS


22.1 Menú público — mobile-first


Estructura funcional vertical:
[Marca / encabezado breve]
[Destacados — solo si existen]
[Categorías en navegación horizontal de acceso rápido]
[Sección de categoría]
  [Producto]
    nombre
    precio
    descripción breve
    opciones informativas
    estado Disponible/Agotado
    imagen opcional
[Secciones siguientes]
[Salsas disponibles — información complementaria]
[CTA persistente: Pedir por WhatsApp]


Reglas UX:
• el contenido útil aparece inmediatamente al entrar;
• categorías desplazan a la sección correspondiente;
• el CTA de WhatsApp permanece accesible durante el recorrido;
• agotados permanecen visibles pero inequívocamente marcados;
• ausencia de imagen no rompe el layout;
• destacados desaparecen por completo si no existen;
• no hay página de producto obligatoria, carrito ni checkout.


22.2 Login administrador


Estructura:
[Taco Loco / Administración]
[Usuario o email]
[Contraseña]
[Ingresar]
[Mensaje de error contextual cuando corresponda]


Reglas:
• una sola acción principal;
• sin dashboard introductorio;
• login correcto lleva directamente a Productos;
• credenciales inválidas no borran innecesariamente el identificador ingresado;
• sesión vencida redirige a login con mensaje claro.


22.3 Listado administrador — Productos


Estructura mobile-first:
[Encabezado: Productos]
[Buscar producto]
[Filtro por categoría]
[Crear producto]


[Producto]
 nombre | precio
 categoría
 [Disponible ↔ Agotado]
 [Editar]


Reglas:
• Disponible/Agotado se cambia sin entrar al formulario;
• feedback inmediato al guardar;
• error revierte o informa claramente el estado real;
• búsqueda simple sí se justifica en admin por velocidad operativa;
• productos despublicados se distinguen de agotados;
• listado puede reorganizarse en tabla en desktop sin cambiar el flujo.


22.4 Edición de producto


Estructura:
[Volver]
[Editar producto]
[Nombre]
[Descripción]
[Precio]
[Categoría]
[Imagen]
[Disponibilidad]
[Publicado]
[Destacado]
[Orden]
[Opciones/modificadores]
[Guardar cambios]


Reglas:
• validación próxima al campo;
• durante guardado se evita doble envío;
• éxito mantiene contexto y confirma cambio;
• error de red conserva datos locales cuando sea razonable;
• no se presenta borrado irreversible como acción primaria.


23. DECISIONES FINALES DE FASE 3


• CTA WhatsApp persistente: APROBADO.
• Destacados condicionales: APROBADO.
• Menú público de página única: APROBADO.
• Navegación por categorías con scroll a sección: APROBADO.
• Producto entendible desde listado: APROBADO.
• Admin sin dashboard: APROBADO.
• Toggle de disponibilidad desde listado: APROBADO.
• Formulario de edición separado: APROBADO.
• Búsqueda pública: DESCARTADA para MVP.
• Búsqueda simple en admin: APROBADA.


24. VALIDACIÓN QA DE UX


Cobertura mínima verificada a nivel de diseño:
• happy path cliente;
• navegación por categorías;
• producto agotado;
• ausencia de imagen;
• categoría vacía;
• error de carga pública;
• login inválido;
• sesión vencida;
• cambio rápido de disponibilidad;
• guardado exitoso;
• validación de formulario;
• error de servidor/red;
• uso mobile-first y adaptación a tablet/desktop;
• accesibilidad mínima por texto, foco, contraste y tamaño táctil.
