﻿ALC-001 — ALCANCE FUNCIONAL MVP
Taco Loco Foodtrack
CuyoConsulting and Development
Fecha: 07/08/2026
Estado: CERRADO PARA FASE 1 / sujeto solo a datos de configuración no bloqueantes


1. OBJETIVO
Definir con precisión qué incluye y qué no incluye la primera versión de Taco Loco Foodtrack, de modo que las siguientes fases —modelo funcional, UX, UI, diseño técnico, QA y construcción— trabajen sobre un alcance estable.


El MVP tiene como objetivo reemplazar la carta estática por un menú digital mobile-first accesible mediante QR, permitir que Taco Loco mantenga su catálogo sin depender de un desarrollador y conservar el canal de pedido actual por WhatsApp sin construir todavía un sistema de pedidos propio.


2. ACTORES DEL MVP
2.1 Cliente
Persona que escanea el QR desde su teléfono para consultar el menú. No necesita registrarse, iniciar sesión ni instalar una aplicación.


2.2 Administrador de Taco Loco
Persona autorizada para mantener el catálogo, precios, imágenes, disponibilidad y configuración básica. Para el MVP se contempla un único perfil administrativo funcional; no se diseñará una matriz compleja de roles y permisos.


3. ALCANCE — MENÚ PÚBLICO
El MVP público DEBE permitir:


• Abrir el menú desde una URL pública accesible mediante QR.
• Utilizar el menú sin autenticación ni instalación.
• Navegar correctamente desde teléfonos móviles como caso principal de uso.
• Ver la identidad de Taco Loco adaptada a una interfaz digital.
• Navegar por categorías del menú.
• Visualizar productos pertenecientes a cada categoría.
• Mostrar para cada producto, cuando corresponda: nombre, descripción, precio, imagen, disponibilidad y opciones/modificadores informativos.
• Diferenciar visualmente productos disponibles y agotados.
• Ocultar del menú público productos o categorías desactivados por administración.
• Permitir productos destacados mediante una marca simple de “destacado”; no implica motor de promociones ni reglas de precios.
• Ofrecer un acceso visible a WhatsApp para continuar el pedido por el canal tradicional de Taco Loco.
• Abrir WhatsApp con un mensaje inicial configurable o prellenado básico. El MVP no construirá el pedido automáticamente a partir de una selección de productos.
• Funcionar correctamente en los tamaños de pantalla móviles definidos durante UX/QA.


4. ALCANCE — ADMINISTRACIÓN
El MVP administrativo DEBE permitir:


4.1 Acceso
• Login de administrador.
• Acceso protegido a /admin o ruta equivalente.
• Cierre de sesión.


4.2 Categorías
• Crear categoría.
• Editar nombre y datos básicos.
• Activar/desactivar categoría.
• Definir orden de visualización.
• Eliminar o retirar una categoría mediante el comportamiento técnico que se defina posteriormente.


4.3 Productos
• Crear producto.
• Editar producto.
• Modificar nombre.
• Modificar descripción.
• Modificar precio.
• Asignar categoría.
• Cargar/cambiar imagen cuando corresponda.
• Marcar disponible/agotado.
• Activar/desactivar publicación.
• Marcar/desmarcar como destacado.
• Definir orden de visualización.


4.4 Opciones / modificadores
El modelo debe soportar opciones simples asociadas a productos, por ejemplo:
• carne a elección;
• salsa a elección;
• variantes simples cuando existan en la carta.


La gestión exacta de grupos, obligatoriedad y cardinalidad se cerrará en MEN-001. En este MVP las opciones se utilizan principalmente para representar correctamente el catálogo. No constituyen todavía un configurador de pedido o carrito.


4.5 Configuración básica
• Número o destino de WhatsApp utilizado por el CTA público.
• Mensaje inicial básico del vínculo de WhatsApp.
• Datos mínimos de presentación que se decidan durante UI, únicamente si se considera necesario administrarlos y no dejarlos como configuración estática.


5. DECISIONES FUNCIONALES CERRADAS
• El menú público es el producto principal del MVP.
• El cliente no inicia sesión.
• El administrador sí requiere autenticación.
• El negocio puede cambiar precios cuando quiera; la frecuencia de cambio no condiciona la arquitectura funcional.
• La cantidad de mesas no forma parte de los requisitos de esta versión.
• No habrá pedido asociado a mesa en el MVP.
• WhatsApp se integra como continuidad del proceso actual, no como sistema de pedidos interno.
• “Destacados” será una capacidad simple de presentación, no un motor promocional.
• “Agotado” es un estado operativo explícito del producto.
• La carta actual es fuente de contenido y de identidad visual, pero no se reproducirá como una imagen estática.
• Las salsas y otras elecciones podrán representarse como opciones/modificadores cuando conceptualmente correspondan, en lugar de forzarlas siempre como productos independientes.


6. FUERA DE ALCANCE DEL MVP
Queda expresamente fuera de esta primera versión:


• Carrito de compras.
• Creación de pedidos dentro de la plataforma.
• Pedido por mesa.
• Identificación obligatoria de mesas mediante QR.
• Seguimiento de estados de pedido.
• KDS / pantalla de cocina.
• Gestión de mozos.
• Caja / POS.
• Pagos online.
• Integración con Mercado Pago u otras pasarelas.
• Delivery propio.
• Cálculo de zonas o costos de envío.
• Take away administrado como flujo interno de pedido.
• Inventario.
• Stock por ingrediente.
• Recetas.
• Costos gastronómicos.
• Gestión de proveedores.
• Analítica avanzada.
• Reportes comerciales complejos.
• Programa de fidelización.
• Registro/login de clientes.
• Notificaciones push.
• Aplicación Android/iOS nativa.
• PWA/offline como requisito.
• Multi-sucursal.
• Multi-tenant.
• Roles administrativos complejos.
• Auditoría empresarial completa.
• Design System corporativo completo.


7. REQUISITOS NO FUNCIONALES DE ALTO NIVEL
Estos requisitos se detallarán posteriormente en arquitectura y QA, pero condicionan el alcance desde ahora:


• Mobile-first.
• Interfaz responsive.
• Navegación sin necesidad de zoom.
• Precios y disponibilidad claramente legibles.
• Rendimiento adecuado para conexión móvil.
• Imágenes optimizadas para web.
• HTTPS en producción.
• Administración protegida mediante autenticación.
• Validación de datos de entrada.
• Accesibilidad básica: contraste, foco, etiquetas y controles utilizables.
• Estados de carga, error y ausencia de contenido definidos.
• URL pública estable para evitar reemplazar los QR ante cambios internos de infraestructura.


8. REGLAS DE NEGOCIO DE ALTO NIVEL
RN-01 — Solo categorías activas se muestran al cliente.
RN-02 — Solo productos publicados/activos se muestran al cliente.
RN-03 — Un producto agotado puede permanecer visible, pero debe identificarse inequívocamente como no disponible. La presentación exacta se define en UX/UI.
RN-04 — El precio visible es el precio vigente almacenado para el producto.
RN-05 — Un producto pertenece como mínimo a una categoría para formar parte de la navegación normal.
RN-06 — El orden de categorías y productos debe ser administrable o configurable.
RN-07 — Un producto puede no tener imagen sin impedir su publicación.
RN-08 — Un producto puede tener cero o más opciones/modificadores.
RN-09 — El CTA de WhatsApp utiliza un destino configurado por Taco Loco.
RN-10 — El CTA de WhatsApp no confirma, registra ni garantiza un pedido dentro de Foodtrack.
RN-11 — El acceso administrativo requiere una sesión autenticada.
RN-12 — No existe dependencia funcional con número de mesa para mostrar el menú.


9. CRITERIOS DE ACEPTACIÓN DE ALTO NIVEL
El alcance de Fase 1 se considerará correctamente implementado en el futuro si:


• un cliente puede escanear el QR y consultar el menú desde un celular sin login;
• puede recorrer todas las categorías activas;
• puede leer nombre, descripción, precio y disponibilidad de los productos;
• los productos agotados son distinguibles;
• el CTA de WhatsApp abre correctamente el canal configurado;
• un administrador autenticado puede cambiar un precio y el menú público refleja el nuevo valor;
• un administrador puede marcar un producto agotado y el menú refleja el estado;
• puede crear, editar, activar y desactivar productos y categorías;
• puede gestionar las imágenes requeridas;
• los datos administrativos no son editables desde el área pública;
• el menú mantiene una experiencia utilizable en los dispositivos definidos por QA.


10. SUPUESTOS Y DATOS DE CONFIGURACIÓN PENDIENTES
Los siguientes datos NO bloquean el cierre del alcance y pueden definirse antes del release:


• número definitivo de WhatsApp;
• dominio/URL definitiva;
• textos exactos de contacto;
• fotografías definitivas de cada producto;
• logo y assets finales en calidad adecuada;
• algunos nombres/ingredientes/precios dudosos de la carta, que se validarán en MEN-001.


11. RIESGOS FUNCIONALES ACTUALES
R-01 — Cargar datos incorrectos desde las imágenes originales de la carta. Mitigación: MEN-001 será la fuente canónica del catálogo.
R-02 — Sobrecargar el MVP convirtiendo WhatsApp en un sistema de pedidos. Mitigación: limitar la integración a CTA/enlace.
R-03 — Diseñar opciones como si ya existiera carrito. Mitigación: representar el dominio correctamente pero implementar solo lo que consume el menú actual.
R-04 — Perder identidad visual al simplificar la carta. Mitigación: Fase UI específica con referencias originales y mockups aprobados.
R-05 — Hacer un panel demasiado complejo. Mitigación: priorizar edición rápida de precio, disponibilidad y catálogo desde móvil.


12. RESULTADO DE LA FASE 1
Alcance funcional del MVP: CERRADO.


No quedan decisiones funcionales de alto nivel que impidan continuar a la Fase 2. Los datos aún dudosos pertenecen al catálogo/contenido o a configuración de release y no justifican mantener abierta esta fase.
