1. PROPÓSITO
Definir la arquitectura técnica mínima correcta para implementar el MVP ya cerrado en ALC-001 y MEN-001, respetando UX-001 y la dirección UI vigente. El objetivo es llegar a construcción con decisiones suficientes, sin incorporar complejidad de fases futuras.


Principio rector: arquitectura proporcional. Elegir la solución más simple que resuelva correctamente el menú público y su administración, mantenga seguridad y calidad, y permita evolución razonable sin construir hoy sistemas que aún no existen.


Fuentes canónicas:
• ALC-001 — Alcance funcional MVP — CERRADO.
• MEN-001 — Catálogo y modelo funcional del menú — CERRADO.
• UX-001 — Flujos críticos y arquitectura de experiencia — CERRADO.
• UI-001 / UI-002 — Dirección visual y blueprint de pantallas — Fase 4 en progreso.
• PRE-DEV-002 — Proceso profesional, roles y gate de construcción.


2. REQUISITOS TÉCNICOS QUE CONDICIONAN LA SOLUCIÓN
• Menú público accesible por URL/QR sin autenticación.
• Mobile-first y buen rendimiento en conexión móvil.
• Administración autenticada y utilizable desde teléfono.
• CRUD operativo de categorías y productos.
• Cambio rápido de precio y disponibilidad.
• Publicación/ocultamiento independiente de disponibilidad.
• Productos destacados simples.
• Imágenes opcionales y reemplazables.
• Opciones/modificadores simples sin carrito ni motor de pedidos.
• Configuración de WhatsApp.
• HTTPS obligatorio en producción.
• URL pública estable.
• Validación de entradas y tratamiento de errores.
• No se requieren microservicios, colas, Redis, CQRS ni event sourcing.


3. ALTERNATIVAS ARQUITECTÓNICAS EVALUADAS


3.1 Opción A — Next.js full-stack + PostgreSQL
Un único producto desplegable contiene interfaz pública, administración, endpoints server-side y lógica de aplicación. La persistencia vive en PostgreSQL.


Ventajas:
• una sola base de código;
• un solo despliegue principal;
• sin CORS entre frontend y backend;
• autenticación más simple;
• SSR/server rendering natural para el menú;
• menor costo operativo;
• suficiente para el alcance real del MVP.


Riesgo principal: acoplar demasiado UI y dominio. Mitigación: estructura modular por capacidades y lógica fuera de componentes/páginas.


3.2 Opción B — Next.js + API NestJS separada + PostgreSQL
Frontend y backend como aplicaciones independientes.


Ventajas:
• separación técnica fuerte;
• API reutilizable por clientes futuros;
• buen encaje si el producto creciera hacia operación compleja.


Costos actuales:
• dos aplicaciones y dos pipelines/despliegues;
• más configuración de autenticación, CORS y contratos;
• mayor superficie de fallos;
• más trabajo sin valor visible para el MVP.


3.3 Decisión
SE ADOPTA Opción A: monolito modular full-stack con Next.js + TypeScript + PostgreSQL.


NestJS no se descarta para una evolución futura. Solo se extraerá un backend independiente si aparece una necesidad real: múltiples clientes, integraciones, operación compleja, escalado independiente o crecimiento del dominio de pedidos. No se construirá esa separación por anticipado.


4. STACK TÉCNICO
• Runtime: Node.js en versión LTS soportada al iniciar construcción.
• Lenguaje: TypeScript con modo estricto.
• Framework full-stack: Next.js, versión estable fijada en el lockfile al iniciar construcción.
• UI: React dentro de Next.js.
• Base de datos: PostgreSQL.
• ORM/migraciones: Prisma.
• Validación: esquemas server-side con Zod o equivalente mantenido; decisión preferida: Zod.
• Procesamiento de imágenes: Sharp o equivalente server-side.
• Almacenamiento de imágenes: object storage S3-compatible; proveedor inicial recomendado: Cloudflare R2.
• Reverse proxy/TLS: Caddy en VPS.
• Contenedores: Docker + Docker Compose.
• Repositorio/CI: GitHub + GitHub Actions.
• Registry de imagen: GitHub Container Registry o equivalente.


Regla de versiones: no se congela en este documento una versión menor que pueda quedar obsoleta antes de construir. Las versiones exactas se fijarán en package.json/lockfile y Dockerfile al abrir el primer ticket de construcción.

7. MODELO DE DATOS FÍSICO — PROPUESTA V1


7.1 AdminUser
• id: UUID.
• email: único.
• passwordHash.
• active: boolean.
• createdAt.
• updatedAt.
• lastLoginAt: opcional.


No existe registro público de administradores. El usuario inicial se crea mediante seed o procedimiento administrativo controlado.


7.2 Session
Sesiones persistentes server-side asociadas al administrador, administradas por la solución de autenticación elegida. No almacenar tokens de autenticación en localStorage.


7.3 MenuSettings
Registro único para configuración del menú:
• id.
• businessName.
• whatsappPhone.
• whatsappMessage.
• currency: ARS.
• optional presentation fields si UI los requiere.
• updatedAt.


7.4 Category
• id: UUID.
• name.
• slug.
• active.
• sortOrder: integer.
• archivedAt: nullable.
• createdAt.
• updatedAt.


7.5 Product
• id: UUID.
• categoryId: FK Category.
• name.
• no se requiere slug de producto en el esquema inicial; solo se agregará si una URL pública o navegación real lo necesita.
• description: nullable.
• priceAmount: integer expresado en pesos ARS para este MVP.
• imageKey: nullable; guarda la clave del objeto, no una URL rígida.
• imageAlt: nullable.
• available: boolean.
• published: boolean.
• featured: boolean.
• sortOrder: integer.
• archivedAt: nullable.
• createdAt.
• updatedAt.


Regla: disponibilidad y publicación son dimensiones distintas. Un producto puede estar publicado y agotado; un producto no publicado no aparece al público.


7.6 ModifierGroup
• id: UUID.
• name.
• active.
• sortOrder.


Ejemplos canónicos: Salsa a elección, Carne a elección, Sabor de daikiri.


7.7 ModifierOption
• id: UUID.
• modifierGroupId: FK.
• name.
• priceDelta NO se incluye en el esquema inicial porque el MVP no tiene adicionales con precio ni motor de pedido; se agregará mediante migración si aparece una necesidad real.
• active.
• sortOrder.


7.8 ProductModifierGroup
Relación N:M entre Product y ModifierGroup.
Campos recomendados:
• productId.
• modifierGroupId.
• required: nullable/boolean según regla aplicable.
• minSelections: nullable.
• maxSelections: nullable.
• sortOrder.


La cardinalidad se coloca en la asociación para no asumir que un mismo grupo tendrá siempre las mismas reglas en todos los productos. En el MVP estas reglas son informativas: no existe selección persistida ni carrito.


8. REGLAS DE PERSISTENCIA
• IDs internos UUID.
• Precios almacenados como enteros; no usar float.
• Todas las escrituras administrativas se validan en servidor.
• archivedAt se utiliza para retiro lógico cuando se requiera eliminar, evitando pérdida accidental de datos.
• El área pública filtra siempre archivedAt IS NULL, categorías activas y productos publicados.
• available=false NO elimina el producto del menú; lo muestra como Agotado.
• sortOrder es explícito para categorías, productos, grupos y opciones.
• Las operaciones que modifiquen varias entidades relacionadas deben usar transacción PostgreSQL/Prisma.


9. CONTRATOS PRINCIPALES


9.1 Público
Contrato público conceptual: MenuReadModel. La página server-side consumirá directamente el servicio de aplicación. GET /api/public/menu solo se expondrá si una interacción cliente real lo necesita; no es requisito para el primer render.
Devuelve una representación preparada para consumo público con:
• configuración pública necesaria;
• categorías activas ordenadas;
• productos publicados/no archivados ordenados;
• disponibilidad;
• destacados;
• imagen cuando exista;
• modificadores informativos.


No expone datos administrativos, hashes, campos internos innecesarios ni elementos archivados.


9.2 Administración
Autenticación:
• POST /api/auth/login
• POST /api/auth/logout
• GET /api/auth/session o mecanismo equivalente de la librería seleccionada.


Categorías:
• GET /api/admin/categories
• POST /api/admin/categories
• PATCH /api/admin/categories/:id
• acción de archivar/reactivar si se requiere.


Productos:
• GET /api/admin/products
• POST /api/admin/products
• GET /api/admin/products/:id
• PATCH /api/admin/products/:id
• PATCH /api/admin/products/:id/availability para cambio operativo rápido.
• acción de archivar/reactivar si se requiere.


Media:
• POST /api/admin/media/products para carga/reemplazo de imagen.


Configuración:
• GET /api/admin/settings
• PATCH /api/admin/settings


Modificadores:
Se administrarán dentro de la edición del catálogo mediante endpoints/acciones simples. No se crea un subsistema independiente mientras no sea necesario.


10. FORMATO DE ERRORES
Los endpoints propios deben devolver errores previsibles y no filtrar trazas internas.


Forma conceptual:
{
  code: string,
  message: string,
  fieldErrors?: Record<string, string[]>
}


Categorías mínimas:
• VALIDATION_ERROR
• UNAUTHORIZED
• FORBIDDEN
• NOT_FOUND
• CONFLICT
• MEDIA_INVALID
• INTERNAL_ERROR


11. AUTENTICACIÓN Y SESIONES
Estrategia elegida:
• autenticación únicamente para administración;
• email/usuario + contraseña;
• password hashing Argon2id o algoritmo moderno equivalente soportado;
• sesión server-side persistente;
• cookie HttpOnly;
• cookie Secure en producción;
• SameSite Lax como baseline;
• expiración y renovación controladas;
• cierre de sesión invalida la sesión server-side;
• no JWT persistente en localStorage;
• no registro público;
• protección/rate limiting del login;
• mensajes de login que no revelen innecesariamente si un usuario existe.


La librería concreta debe ser mantenida y compatible con la versión de Next.js elegida. La estrategia de seguridad es canónica aunque cambie la librería.


12. AUTORIZACIÓN
Un único rol funcional ADMIN para el MVP.
Toda ruta /admin y toda mutación /api/admin/* exige sesión autenticada.
El área pública es de solo lectura.
No se implementa RBAC complejo.


13. IMÁGENES
Proveedor inicial: Cloudflare R2 mediante API S3-compatible.


Flujo:
Admin → carga archivo → servidor valida → procesa/optimiza → sube a R2 → guarda imageKey en Product.


Validaciones mínimas:
• tipos permitidos: JPEG, PNG, WebP;
• validar MIME real y extensión;
• límite de tamaño configurable, baseline 5 MB antes de procesamiento;
• eliminar metadata innecesaria cuando sea posible;
• generar formato web eficiente, preferentemente WebP/AVIF según soporte del pipeline;
• limitar dimensiones máximas;
• nombres de objeto generados por sistema, no confiar en filename del usuario.


Las imágenes públicas se sirven con cache largo porque las nuevas versiones utilizan nuevas object keys. La base de datos no almacena binarios.


14. RENDIMIENTO Y CACHE
El catálogo es pequeño y predominantemente de lectura. No se introduce Redis.


Baseline:
• menú renderizado server-side;
• consulta optimizada única o pequeña cantidad de consultas;
• índices en campos de relaciones, published/active y sortOrder cuando Prisma/PostgreSQL lo justifique;
• imágenes optimizadas y cacheables;
• compresión HTTP;
• assets estáticos con cache largo.


Inicialmente se prioriza consistencia: un cambio administrativo debe reflejarse rápidamente. No se implementará una capa compleja de invalidación de cache hasta que métricas reales la justifiquen.


15. SEGURIDAD
• HTTPS obligatorio.
• secretos solo en variables de entorno/secret store; nunca en repo.
• cookies seguras para sesión.
• validación server-side de todas las mutaciones.
• rate limiting de login y, si corresponde, uploads.
• protección CSRF según mecanismo de sesión/framework elegido.
• headers de seguridad adecuados.
• subida de archivos restringida y procesada.
• evitar exposición de IDs o datos sensibles innecesarios en respuestas públicas.
• dependencias actualizadas y auditadas dentro de CI.
• PostgreSQL no expuesto públicamente a Internet.
• R2 credentials con privilegios mínimos sobre el bucket necesario.

17. CI/CD
Pipeline mínimo en GitHub Actions:
1. instalar dependencias con lockfile;
2. lint;
3. typecheck;
4. tests automáticos definidos para el incremento;
5. build;
6. construir imagen Docker;
7. publicar imagen en registry;
8. desplegar al VPS mediante mecanismo autenticado;
9. ejecutar migraciones Prisma de producción de forma controlada;
10. health/smoke check posterior.


Una migración fallida debe detener release. No ejecutar cambios destructivos de esquema sin estrategia explícita.


18. BACKUPS Y RECUPERACIÓN
PostgreSQL usa volumen persistente, pero el volumen NO cuenta como backup.


Baseline:
• pg_dump automático diario;
• backup comprimido hacia R2/object storage;
• retención propuesta: 7 diarios + 4 semanales;
• secretos de backup separados cuando sea viable;
• prueba de restauración antes del primer release productivo;
• documentar procedimiento de restore.


Las imágenes viven en R2 y deben usar versionado/estrategia de conservación adecuada al costo y necesidad del MVP.


19. OBSERVABILIDAD MÍNIMA
• logs estructurados de servidor.
• request/error correlation ID cuando sea útil.
• endpoint /api/health o equivalente.
• healthcheck de contenedor.
• uptime monitor externo liviano recomendado.
• errores de autenticación y uploads registrados sin guardar contraseñas/tokens.


No se agrega stack pesado de observabilidad hasta necesitarlo.


20. ENTORNOS
Local:
• app local;
• PostgreSQL mediante Docker Compose;
• bucket/dev media separado o emulación compatible si conviene.


Producción:
• VPS;
• PostgreSQL persistente;
• R2 producción;
• secretos independientes.


Staging separado no es obligatorio para este MVP. Antes de release se utilizará entorno local/preview y una validación controlada. Si el costo operativo lo permite, staging podrá agregarse luego.


21. DATOS INICIALES

24. RIESGOS Y MITIGACIONES
R-T01 — El producto crece y el full-stack se vuelve incómodo.
Mitigación: módulos desacoplados y servicios/repositorios; extraer API solo ante necesidad real.


R-T02 — Pérdida de base de datos en VPS.
Mitigación: volumen persistente + backup offsite diario + restore probado.


R-T03 — Upload malicioso o excesivo.
Mitigación: autenticación, validación MIME/tamaño, procesamiento server-side y permisos mínimos de bucket.


R-T04 — Credenciales admin comprometidas.
Mitigación: hash fuerte, cookies seguras, rate limiting, HTTPS y ausencia de registro público.


R-T05 — Cambios administrativos no se reflejan por cache.
Mitigación: no introducir cache de datos compleja inicialmente; priorizar consistencia.


R-T06 — Sobrediseño por funcionalidades futuras.
Mitigación: cualquier capacidad fuera de ALC-001 requiere una nueva decisión de alcance.

29. REVISIÓN CRÍTICA Y AJUSTES DE ARQUITECTURA — 08/08/2026
La propuesta fue revisada contra ALC-001 y MEN-001 para detectar sobrearquitectura y campos incorporados solo por hipótesis futuras.


Ajustes adoptados:
• Se mantiene Next.js full-stack; separar NestJS sigue sin aportar valor al MVP actual.
• Se mantiene PostgreSQL porque el catálogo y las relaciones de modificadores encajan naturalmente en un modelo relacional y la administración requiere consistencia transaccional.
• Se mantiene Prisma por migraciones, tipado y velocidad de implementación; no se introduce una capa ORM adicional.
• Se elimina priceDelta del esquema inicial. MEN-001 lo admitía solo como posibilidad futura y no existe requisito actual de modificadores con precio.
• No se exige slug de producto. No hay página de detalle ni URLs por producto en el MVP.
• El menú público no necesita pasar por una API HTTP interna para renderizarse. El Server Component/página puede consumir el servicio de catálogo directamente. Un endpoint público se agrega solo si una interacción cliente real lo necesita.
• Se mantiene ProductModifierGroup con cardinalidad en la asociación porque es una decisión estructural correcta y evita acoplar reglas de selección al grupo reutilizable.
• Se mantiene archivedAt porque UX descartó la eliminación irreversible como flujo primario y permite retiro seguro sin confundirlo con agotado o no publicado.
• No se agrega Redis, cola, CDN de datos, event bus ni staging dedicado.


Conclusión de revisión:
La solución tiene un único desplegable de aplicación, una base relacional y un almacenamiento externo de media. La complejidad incorporada corresponde a necesidades reales de autenticación, catálogo, imágenes, persistencia y recuperación; no a funciones futuras hipotéticas.
