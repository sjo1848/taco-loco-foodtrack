# QA C10-03 — Intención de pedido y cierre con WhatsApp

Estado: aprobado localmente — 2026-08-10.

## Problema corregido

Antes, el menú solo abría WhatsApp. El pedido no aparecía en la bandeja administrativa porque C8 había definido el alta como manual.

## Implementado

- `POST /api/orders/intents` para registrar una intención pública.
- Validación server-side de producto, disponibilidad, modificadores y precio.
- Estado inicial `RECEIVED` visible en admin.
- Referencia idempotente para evitar duplicados por reintento.
- Rate limit básico por IP para el endpoint público.
- Apertura de WhatsApp después de preparar la intención.
- Mensaje visible: el pedido fue preparado, pero la confirmación sigue pendiente.
- Admin muestra `Menú público` como origen del registro y permite confirmar o cancelar.

## Evidencia

- La intención de `Burrito` creó `TL-0006` en PostgreSQL local.
- La bandeja admin mostró `TL-0006 · Recibido · 1 línea · $10.000`.
- El detalle mostró `Creado por Menú público`, la nota operativa y el evento `Intención preparada desde el menú público`.
- Los precios enviados por cliente no se utilizan: el servidor resuelve el catálogo.
- Typecheck: aprobado.
- Tests: 10 suites y 22 tests aprobados.
- Lint: aprobado.
- Build: aprobado.
- Audit: sin vulnerabilidades conocidas.

## Decisión operativa

El flujo queda cerrado como `registrar intención → abrir WhatsApp → confirmar manualmente`. `RECEIVED` no significa pedido aceptado: significa que Foodtrack ya tiene algo para que el local revise.

## Limitaciones pendientes

La integración no lee respuestas de WhatsApp ni confirma disponibilidad automáticamente. El rate limit actual es una protección base de proceso local; antes de producción deberá complementarse con infraestructura y observabilidad adecuadas.
